# ADR-0001: Архитектура агрегации логов для парка IoT-шлюзов

## Статус

Принято — 2026-04-30

## Контекст

Эксплуатируется парк из ~1000 Linux IoT-шлюзов (ARM-класс, ~256 МБ ОЗУ,
нестабильное соединение). Каждый шлюз пишет локальные лог-файлы от
нескольких сервисов (приложение, система, сеть). Эксплуатационные
требования:

- Логи должны попадать в центральное хранилище за **1–5 секунд** при
  штатных условиях сети.
- Edge-агент должен быть **лёгким**: единицы МБ RSS, минимум CPU,
  без JVM/Python-рантайма.
- Сеть **ненадёжна**: агент обязан буферизовать локально и
  возобновлять отправку при восстановлении связи без потери данных.
- Центральная часть должна горизонтально масштабироваться до
  **десятков тысяч событий/сек** в сумме, с ретеншеном на недели
  для compliance и постмортемов.
- Команда SRE небольшая; **простота эксплуатации** и **стоимость
  хранения** важнее изощрённого full-text поиска.

## Решение

Принимается конвейер **Fluent Bit → Loki → Grafana**:

**Fluent Bit** на каждом шлюзе как log shipper:
- Написан на C, ~5–15 МБ RSS — комфортно укладывается в 256 МБ.
- Нативный output-плагин Loki говорит push API напрямую.
- Встроенная **файловая буферизация** (`storage.type filesystem`)
  обеспечивает устойчивость при перезагрузках и отключениях сети.
- Tail + multiline-парсинг + обогащение метками (host, service, env)
  конфигурируется декларативно.

**Loki** как центральное хранилище логов:
- Модель **индексации по меткам**: индексируется только метаинформация,
  тела логов хранятся как сжатые чанки в объектном хранилище.
  Стоимость хранения **~в 10 раз ниже** Elasticsearch при том же ретеншене.
- Горизонтальное масштабирование через distributor / ingester / querier;
  на старте достаточно **monolithic single-binary**, позже разделяется
  без миграции данных.
- Нативная интеграция с Grafana.

**Grafana** для визуализации, ad-hoc LogQL и алертинга через встроенный
**Ruler / Unified Alerting**, с доставкой через Alertmanager-совместимые
ресиверы (Slack, PagerDuty, email).

**Транспорт**: HTTPS на Loki push API, за NGINX L7-балансировщиком
(терминация TLS, масштабирование пути записи). Каждое устройство отправляет
батчи со snappy-сжатием с интервалом 1–5 секунд.

### Почему не Elasticsearch (ELK / EFK)

| Критерий                       | ELK                                  | Loki                                    |
|--------------------------------|--------------------------------------|-----------------------------------------|
| Стоимость хранения             | Полный inverted index, ~5–10× данных | Индекс только по меткам, чанки в S3     |
| Память на центральных нодах    | Высокая (JVM heap, doc values)       | Низкая (Go, потоковые чанки)            |
| Edge-агент                     | Filebeat (~40 МБ) / Logstash (JVM)   | Fluent Bit (~10 МБ)                     |
| Сложность эксплуатации         | Кластер, ребалансировка шардов       | Stateless reads, S3 как хранилище       |
| Full-text поиск                | Отличный                             | Достаточный (LogQL grep + label filter) |
| Соответствие задаче (ops-логи) | Избыточно                            | По месту                                |

Запросы по логам в основном вида `{host="...", service="..."} |= "error"` —
это ровно сильная сторона Loki. Платить «налог ELK» за Lucene-возможности,
которые нам не нужны, — нерационально.

## Последствия

### Положительные

- Бюджет памяти на edge выдержан (Fluent Bit << 50 МБ).
- Стоимость хранения в ~10 раз ниже ELK; ретеншен расширяется дёшево
  через S3 lifecycle policies.
- Файловый буфер на edge + retry/backoff обеспечивают **at-least-once**
  доставку при многочасовых отключениях без ручного вмешательства.
- LogQL — строгое надмножество label-селекторов и grep; кривая обучения
  SRE, знакомых с PromQL, минимальная.
- Полностью open-source, без vendor lock-in.

### Компромиссы

- LogQL **менее выразителен**, чем Lucene/KQL для свободного текста:
  богатый поиск и агрегации требуют либо аккуратной разметки меток,
  либо `unwrap`/`pattern`-парсинга на стороне запроса.
- **Метки с высокой кардинальностью** (например, request-id как метка)
  взорвут индекс Loki. Дисциплина в дизайне меток обязательна —
  поля высокой кардинальности должны оставаться в теле лога.
- Read path Loki выигрывает от **кеширования чанков** (Memcached/Redis);
  без него крупные исторические запросы медленные.

### Масштабируемость

- **Фаза 1** (≤1000 устройств, ≤10k EPS): monolithic Loki + S3 +
  один Grafana. NGINX опционален.
- **Фаза 2** (рост, multi-tenant, всплески): split на distributor /
  ingester / querier за NGINX, RF=3 на ingester'ах.
- **Фаза 3** (multi-region, всплески приёма, развязка): добавляется
  Kafka между Fluent Bit и Loki — output-плагин Kafka в Fluent Bit зрелый;
  Vector или собственный Go-консьюмер сливает Kafka в Loki. Это изолирует
  push с устройств от доступности Loki и поглощает всплески.

### Сценарии отказа

- **Потеря сети (устройство → центр)**: Fluent Bit заполняет дисковый
  буфер (например, 256 МБ на устройство); при восстановлении сливает
  с retry и экспоненциальным backoff. Логи сохраняются в пределах буфера;
  при переполнении отбрасываются самые старые (поведение настраивается).
- **Переполнение буфера на устройстве**: метрика Fluent Bit, снимаемая
  Prometheus-эндпоинтом, идёт в Grafana и поднимает алерт до того, как
  потеря данных станет молчаливой.
- **Падение Loki ingester**: при RF=3 потеря одной реплики не приводит
  к потере данных. WAL ingester'а проигрывает чанки в памяти при рестарте.
- **Недоступность объектного хранилища**: ingester'ы держат чанки в памяти
  до настроенного возраста; при затяжном инциденте включают backpressure
  на distributor'ы, те отдают 5xx — Fluent Bit ретраит из edge-буфера.
  End-to-end at-least-once сохраняется в пределах ёмкости edge-буфера.
- **Падение Grafana**: только read-only impact; приём не страдает. Alerting
  через Ruler можно вынести в отдельный процесс для повышения доступности.

## Рассмотренные альтернативы

1. **Elasticsearch / ELK stack** — отклонено. Выше стоимость хранения,
   тяжелее edge-агент (Filebeat/Logstash), JVM-эксплуатация, избыточный
   функционал (full-text Lucene, doc-level relevance).

2. **Kafka-конвейер с первого дня** (*Fluent Bit → Kafka → consumer → Loki*)
   — отклонено для Фазы 1 по стоимости/сложности: 3-брокерный Kafka-кластер
   удваивает центральный footprint при ~1000 устройств. Зарезервировано
   как Фаза 3, когда появятся всплески или дополнительные потребители
   (например, ответвление в SIEM).

3. **Гибрид Loki + Kafka (выборочно)** — Fluent Bit при штатной нагрузке
   пишет напрямую в Loki, а при backpressure уходит в Kafka. Привлекательно,
   но операционно сложно (двойной путь, гарантии порядка). Отложено.

4. **Vector вместо Fluent Bit** — Vector сильный кандидат (Rust, схожий
   footprint, богаче трансформации). Отклонено только потому, что у
   Fluent Bit длиннее история на ARM/embedded Linux и меньше бинарь;
   Vector остаётся запасным вариантом.

5. **Прямая отправка из кода приложения (без агента)** — отклонено.
   Привязывает доступность приложения к доступности логирования, тащит
   буферизацию в каждый сервис и ломает допущение «лог в файл — надёжно».
